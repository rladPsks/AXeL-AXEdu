# Vercel 프론트 + Railway 백엔드 배포

구조: 브라우저 → Vercel 정적 React/Vite → `/api/*` rewrite → Railway FastAPI 단일 프로세스 → `/data` 볼륨의 SQLite. API 프로세스 안에서 알림 스레드와 선택적으로 AI 워커 스레드를 실행한다. DB 종류·SQL·migration·업무 규칙은 그대로 유지한다.

운영자가 아래 설정을 한 번 완료하면 방문자는 Python·Node 설치나 로컬 환경변수 없이 Vercel URL로 접속할 수 있다. **현재 앱은 개발용 Bearer 토큰 로그인이 필요하다.** 공개 회원가입·기관 로그인·자동 체험 계정은 아직 없으므로, 링크만으로 누구나 즉시 사용하는 서비스까지 완성되는 것은 아니다. 인증을 없애거나 관리자 토큰을 프론트 코드에 넣지 않는다.

## 1. Railway

1. GitHub 저장소 `rladPsks/AXeL-AXEdu`를 연결한다. 이 설정 파일이 포함된 커밋/브랜치를 선택한다. 현재 작업 브랜치는 `codex/b-foundation`이며 이전 PR #2 병합만으로 최신 코드가 배포되는 것은 아니다.
2. Root Directory는 저장소 루트로 둔다. `backend/`로 지정하면 공통 패키지와 루트 requirements를 찾지 못한다. `railway.json`은 Railpack, 루트 `requirements.txt` 설치, 아래 시작 명령과 `/api/health`를 지정한다. `.python-version`은 Python 3.12를 선택한다. 별도 `RAILPACK_PYTHON_VERSION`이 있으면 3.12와 일치시키거나 제거한다.

   ```sh
   uvicorn backend.main:create_app --factory --host 0.0.0.0 --port $PORT
   ```

3. 백엔드 서비스에 영구 볼륨을 추가하고 **`/data`에 마운트**한다. 환경변수만 설정해서는 영구 볼륨이 만들어지지 않는다.
4. Railway 서비스 Variables를 설정한다.

   | 변수 | 값 |
   |---|---|
   | `SCHOOL_AGENT_DB` | `/data/app.sqlite3` |
   | `SCHOOL_AGENT_RUN_WORKER` | `1` |
   | `OPENAI_API_KEY` | 운영자가 서버에만 입력하는 키 |
   | `OPENAI_MODEL` | 해당 프로젝트에서 사용 가능한 구조화 응답 지원 모델 ID |

   `PORT`는 Railway가 제공한다. `.env.example`은 예시이며 앱이 `.env`를 자동 로딩하지는 않는다. OpenAI 키/모델이 없으면 AI 기능은 준비되지 않은 상태로 표시되지만 일반 업무 API는 사용할 수 있다.
5. 배포한다. replica는 1개로 유지하고 Uvicorn `--workers`나 `--reload`를 추가하지 않는다. 기존 `WEB_CONCURRENCY` 변수가 있다면 `1`로 맞추거나 제거한다. 이 구성은 한 API 프로세스와 스레드가 같은 볼륨 DB를 사용한다. 별도 AI worker 서비스를 동시에 배포할 필요가 없다.
6. Networking에서 공개 도메인을 생성하고 대상 포트가 서비스의 `PORT`와 일치하는지 확인한다. `https://실제도메인/api/health`를 열어 인증 없이 `{"status":"ok"}`가 나오는지 확인한다. 이 응답은 AI 공급자의 동작이나 로그인 성공을 보증하지 않는다.
7. **배포된 컨테이너의 셸/SSH**에서 처음 한 번만 실행한다. Railway CLI를 쓴다면 해당 서비스에 `railway ssh`로 접속한 뒤 실행한다.

   ```sh
   python -m backend.seed --db /data/app.sqlite3
   ```

   출력된 `tokens` 중 `admin` 또는 다른 교직원 토큰으로 접속한다. 토큰은 비밀이며 Git·Vercel 설정·공개 문서에 넣지 않는다. 이 명령은 빈 DB에 가상 학교/계정/사건을 만드는 **시연용 초기화**다. 이미 계정이 있으면 중단하며, 토큰은 8시간 후 만료된다. 토큰 재발급용으로 DB를 삭제하거나 seed를 반복하지 않는다. 장기 서비스에는 정상 로그인·세션 재발급을 별도 구현해야 한다. `railway shell`/`railway run`으로 로컬에서 실행하면 원격 볼륨의 DB가 초기화되지 않는다.

DB migration은 API 시작 시 기존 runner가 실행한다. 볼륨은 실행 컨테이너에 연결되므로 seed를 build/pre-deploy 명령에 넣지 않는다. 재배포 후 사건/파일이 유지되는지도 확인한다.

## 2. Vercel

1. 같은 GitHub 저장소를 연결하고 배포 설정이 있는 브랜치를 선택한다.
2. Root Directory **`frontend`**, Framework **Vite**, Build Command **`npm run build`**, Output Directory **`dist`**로 설정한다. npm 설치는 커밋된 `package-lock.json`을 사용한다.
3. `frontend/vercel.json`의 `RAILWAY_BACKEND_URL`을 실제 Railway 공개 호스트로 교체하고 커밋한다. 예를 들어 `https://RAILWAY_BACKEND_URL/api/:path*`를 `https://학교백엔드.up.railway.app/api/:path*` 형태로 바꾼다. `https://`를 중복으로 넣거나 `/api`를 두 번 넣지 않는다. 이 문자열은 환경변수 이름이 아니라 **직접 교체해야 하는 자리표시자**다.
4. 배포한다. `/api/*` 규칙을 SPA fallback보다 먼저 유지한다. API 주소는 상대 경로를 그대로 사용하므로 프론트 API client와 별도 CORS 설정을 바꿀 필요가 없다. 브라우저는 Vercel 주소로 요청하고 Vercel이 Railway에 전달한다.
5. OpenAI 키·DB 경로·워커 설정은 Railway에만 둔다. Vercel에는 서버 비밀키를 넣지 않는다.

## 3. 배포 후 확인

- Railway와 Vercel 양쪽 `/api/health`가 HTML이 아닌 동일 JSON으로 응답하는지 확인한다.
- Vercel에서 발급받은 교직원 토큰으로 연결 → 사건 조회 → 업무 요청/회신을 확인한다.
- `/cases/demo-case` 같은 상세 URL에서 새로고침하거나 직접 진입해도 404가 없는지 확인한다.
- AI 검토를 요청하고 별도 worker 프로세스 없이 상태가 QUEUED → RUNNING → WAITING_REVIEW로 진행하는지 확인한다. 실제 모델 호출에는 유효한 서버 키/모델이 필요하다. 검토 성공이 업무 적용이나 기관 제출을 뜻하지 않는다.
- 지원 요청의 앱 알림 전달과 사용자 확인이 따로 저장되는지 확인한다.
- 실제 유효한 파일로 작은 크기부터 **앱 한도 10 MiB(10 × 1024 × 1024바이트)**까지 업로드·다운로드를 확인한다. Vercel rewrite 경유 시 413·타임아웃·프록시 제한이 생기는지 Railway 직접 요청과 비교한다. Vercel Functions의 용량 제한을 외부 rewrite의 한도로 단정하지 않는다. 앱이 허용해도 배포 경로에서 10 MiB가 통과한다고 보장하지 않으며 실제 환경에서 검증해야 한다.
- Railway 재배포 후 같은 사건/첨부가 유지되는지 확인한다. 볼륨 삭제는 데이터 삭제이므로 수행하지 않는다.

## 4. 스레드와 로컬 실행

`SCHOOL_AGENT_RUN_WORKER=1`일 때만 lifespan에서 `Worker(app.state.db, app.state.agent_registry).process_once()`를 반복한다. 작업이 없거나 루프 예외가 나면 종료 Event로 중단 가능한 1초 대기를 한다. 알림은 기존 2초 주기를 유지한다. 종료 시 Event를 설정하고 각 스레드를 최대 12초 기다린다.

이미 진행 중인 공급자 호출을 강제로 취소하지는 않는다. 배포 교체/강제 종료로 실행이 중단되면 기존 lease·재시도 복구 규칙을 따른다. 개발용 `python -m backend.worker` 방식은 유지하며, 이 방식을 선택하면 API의 `SCHOOL_AGENT_RUN_WORKER`는 `0`으로 둔다.

이 파일의 설정을 작성한 것과 실제 클라우드 배포/10 MiB 업로드/실제 OpenAI 호출 검증을 완료한 것은 다르다. 실제 도메인·볼륨·환경변수는 운영자가 설정해야 한다.
