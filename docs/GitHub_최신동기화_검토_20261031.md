# GitHub 최신 동기화 검토 — 2026-10-31

## 후속 수정 결과

아래 최초 검토에서 발견한 테스트 실패 4건과 5개 문제를 후속 수정했다. 최초 검토 내용은 당시 상태를 설명하는 기록으로 유지한다.

- 이전 형식의 가짜 AI 응답 3곳을 새 필수 스키마에 맞췄다. 새 결과 필드를 선택 항목으로 바꿔 모델 검증을 약화시키지 않았다.
- 계정 비활성화 테스트는 잔여 담임 업무분장 때문에 차단되는 것을 먼저 확인하고, 업무분장 해제 후 다시 비활성화한다. 실제 권한 제한은 유지했다.
- 과거 사건 이력은 접수 생성·열람·AI 입력 구성 시 사건 참여 권한과 버전을 검사한다. 저장된 AI 실행도 열람과 워커 실행 시 다시 검사한다. 버전 정보가 없는 이전 이력은 표시/새 입력에서 제외하며, 해당 이력이 든 이전 실행은 재생성해야 한다.
- 운영 requirements에 httpx를 추가했다. 개발 의존성 없는 별도 가상환경에 requirements.txt만 설치한 뒤 factory 초기화·lifespan 시작/종료·실제 로컬 HTTP `/api/health` 200 응답을 확인했다. 검증 환경은 Windows Python **3.13.7**이며 Render Python 3.12에서의 실제 배포 검증은 별도다.
- 이전 저장 결과의 새 필드가 없어도 UI가 정상 표시되며, 없는 점검 결과를 수행한 것처럼 표시하지 않는다. 관련 렌더링 테스트 2개를 추가하고 tsx 테스트도 실행되도록 설정했다.
- evidence_used는 실제 검색한 공식 근거 ID만 허용한다. 가짜 근거 ID와 사건 ID를 공식 근거로 제출하는 경우를 회귀 테스트로 차단했다.
- A LLM 설정은 import 시점 상수 대신 호출 시점의 환경변수를 읽는다. import 후 .env 로딩으로 설정된 모델·키를 가짜 전송으로 검증했다.

최종 검증: 백엔드 **135개 통과**, 프론트 **15개 통과**, TypeScript/Vite 빌드 통과, 운영 의존성 전용 환경의 서버 시작·health 확인 통과. SQL 스키마·마이그레이션은 변경하지 않았다.

실제 Render/Vercel 배포·OpenAI/Azure 외부 호출·10MB 업로드·새 전체 흐름의 브라우저 E2E·검색 근거 전체의 영구 실행 스냅샷 보존·A main의 나머지 모듈 통합은 이번 수정 범위에 포함하지 않았다. 즉, 테스트 통과가 계획 전체 또는 실제 배포 완료를 의미하지 않는다.

## 수정 우선순위

### P1 — 새 접수의 과거 이력이 사건 접근 권한을 우회한다

- 위치: `backend/features/intake.py:154`의 이력 검색 및 `:167`의 workflow 저장, 동일 파일의 `get_intake`.
- 검색 조건은 같은 학교와 이름 일치뿐이다. 교직원별 사건 참여 권한을 검사하지 않고 과거 `case_id`, `raw_text`, 접수 정보 등을 새 사건에 복사한다.
- 가상 DB 재현: 관리자만 접근 가능한 접수를 만든 뒤 `outsider` 교사로 직접 조회하면 403. 같은 보호자 이름으로 새 접수를 만들고 새 접수의 `workflow.tools.history`를 조회하면 이전 원문이 포함된다.
- 수정 방향: 이력 검색 단계에 실제 사건 접근 규칙을 적용한다. 저장된 이력·AI 입력도 열람 시점 권한 변경과 원래 사건의 최신성 검사를 거쳐야 한다. 이름만 같다는 이유로 동일 인물로 확정하지 않는다.

### P1 — Render 운영 의존성에 httpx가 빠져 기본 앱 시작이 실패한다

- 위치: `requirements.txt`, `backend/speech.py:6`, `backend/openai_provider.py:13`, `backend/main.py:81`.
- Render는 `pip install -r requirements.txt`만 실행한다. 이 파일에는 fastapi/uvicorn/openai만 있고 음성 모듈이 직접 사용하는 `httpx`는 개발 의존성에만 있다.
- 설치된 `openai==3.41.0`의 의존성 메타데이터는 `httpx2`를 요구한다. `httpx`와 다른 패키지이므로 이를 대신 설치해주지 않는다. fastapi의 일반 설치도 httpx를 필수 설치하지 않는다.
- httpx가 없는 환경을 import 차단으로 모사하면 기본 factory 초기화 중 `ModuleNotFoundError: No module named 'httpx'`가 발생한다. 이는 실제 깨끗한 Render 빌드 검증을 대신한 정적 의존성 확인과 재현이다.
- 수정 방향: 직접 사용하는 httpx를 운영 requirements에 명시하고 개발 의존성 없는 깨끗한 환경에서 factory 시작을 확인한다. Azure 키가 없어도 기본 registry를 만들 때 import가 발생한다.

### P2 — 기존 AI 검토 결과를 열면 프론트가 예외를 낼 수 있다

- 위치: `backend/openai_provider.py:30`, `frontend/src/features/agent-review/index.tsx:295`.
- 새 필수 필드 `response_draft`, `validation_checks`, `evidence_used`가 추가됐지만 기존 저장 결과에는 없다. UI는 `validation_checks.map()`과 `evidence_used.join()`을 바로 호출한다.
- 기존 DB의 성공한 REVIEW_SUPPORT 결과를 새 UI에서 열면 undefined 메서드 호출로 화면이 깨질 수 있다. 기존 결과용 표시 기본값 또는 결과 스키마 버전별 호환 처리가 필요하다.
- 아래 백엔드 테스트 3건도 이전 결과 형식과 새 필수 스키마 불일치의 영향을 받는다. 새 필드를 포함한 성공 테스트와 이전 저장 결과를 읽는 호환 테스트를 구분해야 한다.

### P2 — evidence_used의 허위 근거 ID가 검증 없이 통과한다

- 위치: `backend/openai_provider.py:153` 이후.
- 관찰의 `source_id`만 검사하고 `evidence_used`는 검색된 공식 근거 목록에 속하는지 검사하지 않는다. 프롬프트 지시는 서버 검증을 대신하지 않는다.
- 외부 호출 없는 가짜 모델 재현: sources가 빈 입력에 `evidence_used=['NONEXISTENT-SOURCE']`를 반환해도 adapter가 그대로 수락한다.
- 수정 방향: evidence_used를 실제 검색 결과의 ID 집합과 대조하고 불일치 결과는 검토 불가 상태로 남긴다. 검색에 사용한 근거 내용·위치·버전도 실행 입력과 함께 재현 가능하게 보존한다.

### P2 — 로컬 .env를 사용하는 A 분류기는 설정을 너무 일찍 읽는다

- 위치: `backend/main.py:35`와 `:41`, `config.py:7`, `llm_client.py:13`.
- intake를 import할 때 config의 LLM/OPENAI 값을 상수로 읽고, 이후 `create_app()`에서 .env를 로드한다. 프로세스 환경에는 키가 없고 .env에만 있으면 A 분류기는 계속 미설정 상태로 fallback할 수 있다. B registry는 로드 후 생성되므로 A/B 간 동작도 달라진다.
- 수정 방향: 호출 시점에 환경설정을 읽거나 모든 모듈이 설정을 읽기 전에 로더를 실행한다. Render가 제공하는 실제 환경변수와 로컬 .env 경로를 각각 검증한다.
