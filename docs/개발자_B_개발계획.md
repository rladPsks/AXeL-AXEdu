# 개발자 B 개발 계획

작성일: 2026-10-30
기준: [A·B 통합 확정 계약 v1.5](개발자_AB_통합계약_확정_v1.md)과 현재 B 소스
목표: 교사가 받은 업무를 수행하고, 학교 지원을 요청하고, 관리자가 함께 처리하는 흐름을 화면·API·저장·AI까지 완성한다.

## 1. 현재 위치

개발 진행 갱신: Render 무료 + Vercel 시연 모드·사람의 지원 판단에 이어 원문 정정 버전·학교별 반복 기준·후보·두 사건 대조와 연결/분리를 구현했다. 서버 96개·프론트 13개·시연 브라우저 6개 테스트가 통과했다. 실제 계정/기관 데이터는 변경하지 않았다. 최신 A 연결은 [반복·원문 안내](B_반복비교_원문버전_연결안내.md), 배포는 [Render + Vercel 안내](배포_안내.md)를 따른다. 실제 OpenAI 호출과 실제 클라우드 배포는 아직 검증하지 않았다.

### 완료된 첫 서버 구현

- FastAPI·SQLite 서버, 개발용 Bearer 세션.
- 학교·사건 참여 기반 접근 검사, 사건 버전, 중복 요청 방지, 감사 이력.
- 교사 업무 생성·확인·완료 회신.
- 학교 지원 요청·수신 확인·조치·완료.
- 총괄 인계 요청·수락, B의 미완료 항목 검사 후 종결·재개.
- 기존 서버 테스트 12개 통과 확인.
- OpenAPI 및 A·B 통합 확정 계약 작성.

### 아직 완료되지 않은 범위

실제 운영 인증·보호자 본인 확인, 실제 OpenAI 호출/품질 검증, A 원문·접수·종결 guard/AI handler 연결, 반복 비교·사람의 지원 판단·보고서 연결, 동의 녹취/STT, 대시보드.

일정·업무 재배정·부재 대체·업무분장·학교 설정·구성원 권한·인계 거절/취소를 구현했다. URGENT를 포함한 앱 알림은 전달/확인/실패와 재시도를 구분한다. 사용자 승인 범위 안에서만 권한을 관리한다. 종결 검사는 A의 답변·승인·후속 의무를 아직 포함하지 않는다. 개발 브랜치는 codex/b-foundation이다. PR #2는 과거 0562c4c까지만 병합되어 있으며 이후 기능은 개발 브랜치에 추가되어 있다.

## 2. 담당 경계

| B가 끝까지 담당 | A가 담당하고 B가 연결할 부분 |
|---|---|
| React 공통 구조·레이아웃·라우터·공통 UI·API client·provider | B 기반을 사용하는 A 기능 화면 |
| 서버 공통 진입·DB·권한·감사·버전·멱등 | 접수·사건 상세 기본 화면과 접수 데이터 |
| 공통 AI 실행·복구·공급자 adapter | 분류·검색·응답·톤·번역·보고서 handler |
| 비공개 파일 저장·다운로드 권한 | 자료 등록·검색·보고서 내보내기 기능 |
| 교사 업무·지원·인계·종결 화면/API | 접수·분류·응답 등 A의 기능별 화면 |
| 반복 비교·지원 판단·증거/공문 | B 지원 결정에 근거한 보고서 작성 |
| 동의 녹취·전사·요약 검토 | 보호자 화면·대외 DTO |
| 활동 기록·지원 대시보드 | 보호자 관계 검사는 B가 기반 제공 |

B도 자기 기능의 React 화면을 만든다. A의 기능별 서버 코드를 B가 모두 대신 작성하는 분담은 아니다.

사용자 확정으로 기존 A의 ‘React 공통 구조·레이아웃·API 클라이언트’ 상대점수 4를 B로 이관했다. 이 변경만 반영하면 A 36 / B 44이며 실제 시간 견적은 아니다. 공통 프론트 기반은 추가 이관을 기다릴 항목이 아니라 B의 선행 필수 작업이다.

## 3. 단계별 개발 순서

날짜·소요시간은 정해지지 않았으므로 아래는 의존 순서다. L1부터 연결하고 L2·L3를 같은 원장 위에 확장한다.

### 0단계 — 코드 인계와 협업 기준 고정

**작업**

- 현재 복사본과 원격 `yujinb`의 이력을 확인하고 기존 서버·계약·테스트를 버전 관리에 반영한다.
- 확정 계약과 OpenAPI를 A에게 전달할 묶음으로 준비한다.
- `codex/integration-v1` 통합 브랜치를 B 기반에서 준비하고 기능별 PR 단위를 정한다.
- `.env`, DB, 개발 토큰, 음성·원문 파일은 커밋에서 제외한다.

**완료 조건:** A가 동일 기반 커밋을 받아 서버와 가상 사건을 실행할 수 있고, 같은 사건 ID·버전·API로 연결한다.

### 1단계 — A가 재사용할 공통 서버 기반 완성 [B-01]

**작업**

- `create_app` 내부의 변경 처리·권한·자원 조회를 재사용 가능한 공통 서비스로 추출한다. 기존 API 동작은 유지한다.
- 기능 router·handler 등록 지점을 마련한다.
- 위치 기반 INSERT를 명시 열 INSERT로 정리하고 migration runner·적용 이력을 추가한다.
- A의 별도 접수/사건 확장 테이블을 수용한다. 기존 cases의 ID·owner·OPEN/CLOSED·version을 유지한다.
- 통합 종결 guard 등록 지점을 만들고 A의 미완료 답변·승인·후속 의무 검사를 연결한다.
- 비공개 파일 저장·메타데이터·다운로드 접근 검사 기반을 만든다.
- 보호자 본인/사건 관계 검사 인터페이스와 필드별 열람 경계를 마련한다. 실제 운영 인증 제공자는 별도 결정이 필요하다.

**A에게 제공:** 공통 변경 서비스, router 등록 예시, migration 규칙, closure guard, 파일·관계 검사 인터페이스.

**완료 조건:** 기존 12개 테스트 유지, A의 신규 API가 같은 권한·트랜잭션·버전·감사를 사용한다. 빈 DB와 기존 개발 DB 모두에서 migration을 검증한다. 다운로드·보호자 관계 차단도 해당 기반 테스트로 확인한다.

### 1-프론트 단계 — React 공통 기반 제공 [B 담당 추가 / 상대점수 4]

1단계 서버 정리와 병행해 A가 사용할 최소 프론트 기반부터 제공한다.

**작업**

- `frontend/`에 React·TypeScript·Vite·npm 기반을 구성하고 `/api` 개발 프록시를 설정한다.
- 공통 레이아웃·라우터·사건 shell·탭 연결·로딩/오류/빈 상태 UI를 만든다.
- Bearer 인증·JSON 처리·오류 봉투·멱등 키·version 충돌을 처리하는 공통 API client를 제공한다.
- 단일 TanStack Query provider와 사용자/학교별 캐시·변경 후 무효화 규칙을 구현한다.
- A/B 기능 모듈 등록 예시를 제공하고 공통 파일·lockfile을 B가 관리한다.

**A에게 제공:** 실행 가능한 프론트 기반, API client 사용 예시, 라우트/탭 확장 지점, 세션·캐시 처리 규칙.

**완료 조건:** 프론트 build 성공, `/api/session`·사건·timeline 실조회, 401/403/409 처리, 세션 전환 시 캐시 폐기. A는 공통 구조를 다시 만들지 않고 기능 모듈을 추가할 수 있다.

### 2단계 — 첫 사용자 흐름을 화면까지 연결 [B-02 / L1]

**작업**

- 교사의 내 업무 목록·상세와 사건별 업무 탭을 만든다. 필요한 목록/조회 API를 추가한다.
- 사실 확인·상담·콜백·후속 업무를 구분하고 질문·콜백 필요·지원 담당·원문 접근을 보여준다.
- 확인·완료 회신, 학교 지원 요청, 관리자의 수신 확인·조치·결과 화면을 만든다.
- 현재 총괄·인계 대기·인수 수락·남은 업무·종결/재개를 표시한다.
- 일정·기한·일정 조정 데이터와 담당 화면을 추가한다.
- 401·403·409·중복 클릭·새로고침·재시작 처리를 공통 client와 연결한다.

**A와 연결:** B가 작성한 사건 shell·공통 API client·query provider에 A/B 기능 컴포넌트를 연결한다. A의 실제 접수 사건을 사용한다. A는 사건 기본 정보 콘텐츠와 접수·분류 모듈을 제공한다.

**완료 조건:** ‘접수 → 교사 업무 요청 → 교사 회신 → 지원 요청 → 관리자 확인/결과 → 이력 재조회’가 실제 화면과 동일 DB에서 동작한다. 업무 요청만으로 총괄이 바뀌지 않고 충돌 시 입력을 보존한다.

### 3단계 — 공통 AI 실행과 복구 [B-01]

**작업**

- agent_runs 원장, 시작 API·상태 조회 API, 목적별 handler registry를 구현한다.
- QUEUED/RUNNING/WAITING_REVIEW/SUCCEEDED/FAILED/CANCELLED와 입력 사건 버전을 저장한다.
- 실제 공급자 adapter·서버 키 설정·실행 로그·오류 봉투를 연결한다.
- worker의 중복 점유 방지·재시도·중단 복구를 구현한다.
- 실행 결과 생성과 사건 적용을 분리한다. 오래된 결과의 자동 적용을 막는다.
- A에게 분류·응답·번역·보고서 handler 등록 예시를 제공한다.

**완료 조건:** 실제 API 호출 결과가 재조회되고 화면 이탈·실패·worker 재시작 뒤 복구된다. AI 실패해도 접수·업무·긴급 지원은 사용할 수 있다. 생성 성공을 승인·제출·종결로 표시하지 않는다.

### 4단계 — 대체자·알림·긴급 지원 보완 [B-02]

**작업**

- 학교 업무분장·대체 책임자·부재·권한·알림 설정을 구현한다.
- 미확인 지원·지연 업무 알림과 대체자 연결을 만든다.
- 알림 저장·전달 성공·수신 확인을 분리하고 실패 재시도를 지원한다.
- 인계 거절/취소·대체자 전환은 새 상태/전이 계약을 추가한 후 구현한다. 기존 PENDING/ACCEPTED를 임의 변경하지 않는다.
- AI를 기다리지 않는 긴급 도움 동선과 관리자/대체자 확인을 연결한다.

**완료 조건:** 관리자 부재·미확인·알림 전달 실패에서도 총괄 책임이 비지 않으며 실제 전달 상태를 확인할 수 있다. 알림 채널은 구현 시 정하고 동작한 채널만 시연한다.

### 5단계 — 반복 비교·사람의 지원 판단·보고서 연결 [B-03 / L2]

**작업**

- 동일인/동일 사안 후보, 연결/분리, 추가 증거·공문·원문 버전을 저장한다.
- 이전 답변·미응답·미이행·새 사실·행동 원문을 비교하는 화면과 AI를 만든다.
- 반복/지연 기준은 학교별 설정으로 관리한다. 30일/3회·24시간 등의 설계 예시를 고정 규정으로 취급하지 않는다.
- 학교 내 지원·전문 지원·외부 지원·추가 검토의 사람 결정을 기록한다.
- 결정자·판단 사유·사실/주장/미확인·출처·대상/경로·남은 학교 업무를 snapshot으로 제공한다.
- A의 보고서에 decision_id와 사건 버전을 전달하고 보고서 이후 학교 후속 업무로 돌아오는 흐름을 연결한다.

**완료 조건:** 미응답 재문의·새 증거·신고 표현 사례를 구분하고 반복 수나 감정만으로 자동 이관하지 않는다. A 보고서가 B의 실제 결정을 참조하며 결정 변경 시 오래된 snapshot임을 표시한다. 파일 생성은 기관 제출로 표시하지 않는다.

### 6단계 — 동의 녹취·전사·정정·요약 검토 [B-04 / L3]

**작업**

- 동의 기록·음성 업로드·형식/크기/길이 검사·비공개 다운로드를 연결한다.
- 실제 STT 공급자와 공통 실행기를 연결하고 구간·화자·시각을 저장한다.
- 원본 전사와 정정 버전을 구분하고 음성 대조·정정·요약 검토·사건 연결 화면을 만든다.
- 동의 미확인·철회·권한 변경·STT 실패·재실행을 처리한다.

**완료 조건:** 동의한 가상 음성으로 ‘업로드 → 실제 전사 → 구간 대조 → 정정 → 요약 검토 → 재조회’가 동작한다. 동의 없는 음성은 외부 STT에 전송하지 않으며 수동 메모를 전사 성공으로 표시하지 않는다.

### 7단계 — 활동 기록·지원 대시보드 [B-04 / L3]

**작업**

- 직접 응대·업무 수행·지원 활동을 기록하고 duration_seconds로 시간을 저장한다.
- 기간·학교·권한 범위에 따른 집계 API를 만든다.
- 미확인 지원·지원 처리 현황·업무 유형·기록된 응대시간을 화면에 표시한다.
- 집계에서 해당 사건/활동으로 근거를 열 수 있게 한다.
- 미기록·상담 포함 범위·시간의 의미·Asia/Seoul 날짜 경계를 표시한다.

**완료 조건:** 원장과 집계 숫자가 일치하고 다른 학교/권한 밖 자료는 노출되지 않는다. 미기록을 실제 0으로 단정하지 않으며 교사 순위를 만들지 않는다.

### 8단계 — 전체 통합·실패 복구·시연

**작업**

- A 접수·근거 응답·번역·보고서와 B의 업무·지원·반복·녹취·집계를 같은 사건으로 연결한다.
- A의 흐름을 B가, B의 흐름을 A가 교차 실행한다.
- 권한·중복·동시 수정·미완료 종결·오래된 AI 결과·다운로드·동의·재시작을 검증한다.
- OpenAPI·실행 안내·migration 안내·구현/미구현 목록을 최종 갱신한다.

**완료 조건:** L1~L3의 실제 구현 흐름과 실패/복구 흐름을 실행할 수 있다. 기관 인증·기관 제출 등 별도 외부 연동이 없으면 해당 제한을 명확히 표시한다.

## 4. 우선순위와 의존 관계

| 우선순위 | 내용 | 이유 |
|---|---|---|
| P0 | 기반 공유·공통 서비스·migration·기본 권한 | A의 서버 기능이 안전하게 합쳐지는 선행 조건 |
| P0 | React 공통 구조·레이아웃·라우터·API client·provider | A/B 화면이 같은 기반에서 개발되는 선행 조건 |
| P0 | 교사 업무/지원 화면과 실제 접수 연결 | 가장 먼저 사용 가능한 제품 흐름 확보 |
| P1 | 공통 AI·파일·관계 검사·종결 guard·대체자/알림 | 후속 기능과 전체 권한/복구 완성 |
| P1 | 반복 비교·지원 판단·A 보고서 연결 | L2 지원 판단과 L3 보고서 선행 데이터 |
| P2 | 녹취·대시보드 | 같은 원장·실행기 위에서 L3 완성 |
| 상시 | 계약·테스트·OpenAPI·실패 복구 | 마지막 통합 시점에 결함이 몰리지 않도록 각 단계 적용 |

우선순위는 구현 순서이며 L3를 범위에서 삭제한다는 뜻이 아니다. 1단계 파일 기반 이후 녹취 준비, 2단계 활동 원장 이후 집계 설계는 AI/반복 기능과 독립적으로 진행할 수 있다.

## 5. A에게 넘길 묶음과 받을 묶음

| 시점 | B → A | A → B |
|---|---|---|
| 시작 | 서버 기반 커밋·확정 계약·OpenAPI·가상 seed | 현재 코드 구조와 접수/UI 이식 범위 |
| 공통 기반 | 변경 서비스·권한·migration·closure/file 인터페이스 | 접수 확장 테이블·답변/승인/후속 closure guard |
| 공통 프론트 | React 공통 구조·레이아웃·라우터·API client·provider·사건 shell | 기능별 라우트/탭 연결 요구와 A 기능 모듈 |
| 첫 화면 | 업무·지원 React 모듈·조회/변경 API | 접수·사건 기본 정보·분류 화면/API |
| AI | 실행 API·handler 등록·복구 방식 | 목적별 AI handler·결과 schema |
| 보고서 | 사람의 지원 결정 snapshot·출처·남은 업무 | 보고서 생성/검토/내보내기 결과와 후속 연결 |
| 통합 | B 검증 사례·실행 안내 | A 흐름 검증 사례·통합 수정 사항 |

이 표는 준비할 산출물이며 A에게 메시지나 파일을 이미 전송했다는 의미는 아니다.
