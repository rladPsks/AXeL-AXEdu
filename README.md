# AXeL-AXEdu | CARE Agent

> 학교 민원대응팀을 위한 **맥락 기반 민원 분류·업무 라우팅·근거 제시 에이전트**

CARE는 **Context-Aware Routing & Evidence-grounded Agent**의 약자입니다. 학교에 접수된 문의·민원을 분석해 처리에 필요한 업무를 정리하고, 학교 민원 처리 기준 및 기존 이력을 참고해 담당 역할과 응답 초안을 제안하는 프로토타입입니다.

현재 프로젝트는 2026 AX-Edu 해커톤 본선 영역 ① 교사 지원, T1 **「민원 창구는 생겼지만, 교사는 여전히 혼자다」**를 대상으로 합니다.

---

## 1. 해결하려는 문제

학교 대표 창구로 민원을 접수하더라도 민원의 성격과 담당 업무를 구분하기 어렵거나, 학생을 가장 잘 아는 담임교사에게 행정적 응대까지 다시 전달되는 일이 생길 수 있습니다.

CARE Agent는 민원을 단순히 분석하는 데서 끝나지 않고 사건·업무·지원·기록을 연결해 학교의 실제 민원 처리 흐름을 수행하도록 설계합니다.

- 문의·상담·행정 민원의 성격과 긴급도 구조화
- 하나의 복합 민원에 섞인 요구를 여러 개의 처리 업무(Action Item)로 분해
- 학교 업무분장 기준에 따른 담당 역할 후보 추천
- 학교민원 처리 매뉴얼 등 근거 문서 검색 및 출처 표시
- 이전 처리 이력과 미완료 조치 확인을 통한 반복 민원 검토 지원
- 담임에게 전체 민원을 전달하는 대신 필요한 사실 확인과 행동만 요약
- 담당자 검토·승인 및 처리 이력 기록 지원

## 2. 전체 처리 흐름

```text
민원 접수
   |
   v
내용 구조화 및 유형·긴급도 예비 분류
   |
   v
기존 민원 이력 및 미완료 조치 확인
   |
   +---------------------------+
   |                           |
   v                           v
학교 업무분장 기준 조회       학교 규정·매뉴얼 검색
   |                           |
   +-------------+-------------+
                 |
                 v
       담당 역할·필요 행동 추천
                 |
                 v
       근거를 포함한 응답 초안
                 |
                 v
       담당자 검토 및 승인 대기
                 |
                 v
       처리 결과·이력 기록
```

모든 결과는 담당자 검토를 위한 제안입니다. 법적 판단, 교육활동 침해 여부 확정, 민원 거부·종결, 답변 발송 및 외부기관 이관을 자동으로 결정하지 않습니다.

## 3. 핵심 설계 원칙

### 3.1 Complaint-to-Action Decomposition
한 민원에 상담, 사실 확인, 학교 차원의 조치 요청 등이 섞인 경우 이를 하나의 담당자에게 통째로 전달하지 않고 개별 처리 업무로 나누는 것을 목표로 합니다.

### 3.2 History-Aware Review
같은 내용의 재문의라도 이전 민원이 미답변 상태인지, 조치가 완료됐는지, 새로운 사실이 추가됐는지 확인해야 합니다. 반복 횟수만으로 부당 민원이나 교육활동 침해를 확정하지 않습니다.

### 3.3 Evidence-Grounded Routing & Response
담당 역할과 응답 초안에는 가능한 한 근거 문서, 페이지, 적용 범위를 표시합니다. 근거가 부족하거나 학교별 기준 확인이 필요한 경우 답변을 보류하고 사람에게 검토를 요청합니다.

### 3.4 Human-in-the-loop
AI는 분류·검색·요약·추천을 담당하고, 담당자는 결과를 수정·승인합니다. 최종 책임과 공식 처리는 학교의 권한 체계에 따릅니다.

## 4. 현재 구현 범위

이 저장소는 **초기 실행 가능한 프로토타입 골격**입니다.

| 영역 | 현재 구현 | 상태 및 제한 |
|---|---|---|
| 민원 입력 | Streamlit 접수 폼 | 구현 |
| AI 분류 | Structured Output 기반 LLM 분류 + 규칙 fallback | 구현 |
| 담당 추천 | 역할 템플릿 기반 라우팅 | 실제 학교 업무분장 검증 필요 |
| 반복 검토 | 사건 DB에서 동일인·학생 관련 후보 검색, 미응답·유사도 맥락 비교 | 구현(고도화 예정) |
| 근거 검색 | 매뉴얼 발췌 청크의 키워드 검색 | 임베딩·하이브리드 검색 기반 정식 RAG 아님 |
| 응답 초안 | 교직원 확인 결과 + 검색 근거를 반영한 LLM 초안 | 구현(최종 발송은 사람 검토) |
| 처리 기록 | SQLite Case/Task/Event/AI Run/Support Request 저장 | 구현 |
| 테스트 | 기본 파이프라인 테스트 파일 | 실행 환경에서 테스트 수행 필요 |

**중요:** 현재 AI 분류와 응답 재생성은 실제 LLM API를 사용하며 실패 시 규칙 기반 fallback으로 복구합니다. 검색은 아직 BM25 계열 lexical retrieval 중심이므로 의미 임베딩 기반 Hybrid RAG는 후속 고도화 대상입니다. 교육활동 침해 확정, 외부 이관, 제재, 공식 답변 발송은 자동 실행하지 않습니다.

## 5. 기술 스택

| 구성 | 기술 | 역할 |
|---|---|---|
| UI | Streamlit | 민원 접수, AI 결과, 처리 이력 시연 |
| Language | Python | AI·검색·업무 규칙 구현 |
| Schema | Pydantic | 분류 결과 및 처리 데이터 구조 검증 |
| Storage | SQLite | 데모 민원·처리 이벤트 저장 |
| LLM | OpenAI Responses API | 구조화 분류, 사건 재검토, 응답 초안 |
| Retrieval | 키워드 검색(현재) → Hybrid RAG 확장 | 매뉴얼·학교 규정 근거 검색 |
| Agent workflow | Stateful Python workflow + SQLite | Case 생성, Action Router, Task 실행, 교사 회신 후 재실행, 지원 요청, 타임라인 |

기한이 제한된 해커톤 프로토타입에서는 Streamlit과 Python 중심의 단일 실행 구조를 우선합니다. LangGraph, 벡터 DB, 외부 인증 및 실제 학교 시스템 연동은 필요성과 시간에 따라 확장합니다.

## 7. 로컬 실행 방법

### 7.1 사전 준비
- Python 3.10 이상 권장
- Git
- 가상환경 생성 및 패키지 설치 권장

### 7.2 설치 및 실행

**Windows PowerShell**

```powershell
git clone https://github.com/rladPsks/AXeL-AXEdu.git
cd AXeL-AXEdu
git checkout feat/ai-agent-foundation

python -m venv .venv
.venv\Scripts\Activate.ps1

streamlit run app.py
```

**macOS / Linux**

```bash
git clone https://github.com/rladPsks/AXeL-AXEdu.git
cd AXeL-AXEdu

python -m venv .venv
```

## 8. 환경변수와 보안

필요한 경우 `.env.example`을 복사해 로컬 `.env` 파일을 만들고 실제 값을 설정합니다.

```bash
cp .env.example .env
```

예시 변수:
- `LLM_API_KEY`
- `LLM_MODEL`
- `LLM_BASE_URL`

실제 API 키, 비밀번호, 토큰, Streamlit secrets는 Git에 커밋하지 않습니다. `.gitignore`가 이를 제외하도록 구성되어 있지만, 이미 추적 중인 파일이나 커밋된 비밀정보를 자동으로 제거하지는 않습니다.

## 9. 데이터 출처와 적용 범위

현재 초기 데이터는 팀이 검토한 교육부·한국교육개발원 「학교민원 처리 매뉴얼」 요약과 팀 내부 기준 정리를 바탕으로 구성했습니다.

- `manual_rules.json`: 민원 종류와 처리 수준 요약
- `manual_chunks.json`: 정의, 담당자 배분, 표준모델 처리 기한, 특이민원, 반복 민원, 이관 서류 관련 페이지 요약
- `routing_rules.json`: 매뉴얼의 역할 예시를 바탕으로 만든 **학교별 업무분장 확인 전 템플릿**
- `risk_rules.json`: 위험 신호를 검토하기 위한 보조 기준

매뉴얼의 처리 기한은 표준모델안일 수 있으며, 실제 학교의 처리 기준과 법령상 개별 처리기간을 구분해야 합니다. 충북교육청 안내서의 지역 운영 절차를 타 시도에 그대로 적용하지 않습니다.

**운영 전 검증 필수 항목**
1. 원문 PDF와 인용 페이지·문구 대조
2. 최신 법령 및 교육청 지침의 유효성 확인
3. 대상 학교의 학년도별 업무분장표와 승인 체계 반영
4. 학교별 규정·학사일정의 시행일 및 적용 범위 확인
5. 교무부장 등 현장 담당자의 라우팅·처리 기준 검수

## 10. 개인정보 및 안전 원칙

- 데모에는 가상 민원과 가명 식별자만 사용합니다.

- 긴급 안전 사안은 AI 결과만 기다리지 않고 학교의 기존 긴급 대응 절차를 따릅니다.
- 민원 답변 발송, 민원 종결, 교육활동 침해 확정, 외부기관 이관은 자동 실행하지 않습니다.

## 10. 법령 중심 지식베이스와 RAG 기준

RAG는 교육부 매뉴얼만 검색하지 않습니다. 법률·시행령·교육청 지침·학교 자체 규정·정책자료를 문서 성격과 시행일로 구분해 관리합니다.

### 현재 포함한 법령
- 초·중등교육법 제35조~제37조 및 2026년 10월 29일 시행 학교민원 대응 규정
- 초·중등교육법 시행령 제65조: 학교민원 중지 요청, 전화·면담 종료, 퇴거 및 일시적 출입 제한 절차
- 민원 처리에 관한 법률 제4조·제7조·제23조
- 민원 처리에 관한 법률 시행령 제4조·제14조·제21조
- 교원의 지위 향상 및 교육활동 보호를 위한 특별법 제18조~제20조 및 제26조
- 개인정보 보호법 제15조·제16조·제17조·제18조·제29조

### 근거 우선순위
1. 법률
2. 시행령
3. 해당 시도교육청 조례·교육규칙·공식 절차
4. 교육부 공식 매뉴얼
5. 해당 학교 규정·학사일정·업무분장
6. 정책계획·보도자료·통계

정책계획과 보도자료는 정책 방향 및 과거 통계를 설명하는 보조 자료이며 법률상 의무의 근거로 사용하지 않습니다. 충북교육청의 세부 절차는 다른 시도에 자동 적용하지 않습니다.

### 시행일 관리
RAG는 질문 기준일에 시행 중인 조문을 우선 검색합니다. 공포되었지만 아직 시행되지 않은 개정 조문은 별도 보관하며 시행일이 도래한 이후에만 현행 근거로 검색하도록 구성합니다.

2026년 10월 30일 기준으로 교원지위법 제18조의 2026년 11월 20일 시행 예정 개정과 제19조의 2026년 12월 3일 시행 예정 개정은 현행 조문과 분리해 관리합니다.

### 개인정보 보호
학생·보호자·교직원 민원 원문을 외부 LLM API로 전송하기 전에는 수집·이용 근거, 최소수집, 제3자 제공 및 목적 외 이용, 안전조치 요건을 검토해야 합니다. 실제 개인정보가 포함된 원문을 개발용 저장소나 외부 모델에 그대로 전송하지 않습니다.

### RAG 데이터 파일
- `data/source_registry.json`: 법령·시행령·매뉴얼·정책자료의 출처와 시행일
- `data/legal_chunks.json`: 조문 단위 법령 검색 데이터
- `data/policy_chunks.json`: 정책계획·보도자료 근거
- `data/rag_policy.json`: 출처 우선순위, 시행일 필터, 인용·안전 기준
- `data/manual_chunks.json`: 학교민원 처리 매뉴얼 발췌

현재 검색은 프로토타입용 키워드 검색입니다. 임베딩·하이브리드 검색·재정렬기를 결합한 정식 RAG는 후속 구현 범위입니다.
